### Programming the MEGA65 — Chapter 1: Introduction 

Oct 4, 2026 · Updated Oct 11, 2026 · @Craig Taylor 

#### What the MEGA65 Is 

The MEGA65 is an 8-bit home computer, built in the 2020s to the design of a machine Commodore never released. It looks and feels like a classic Commodore: a full-size keyboard with a built-in 3.5" floppy drive, a BASIC prompt at power-on, and a built-in machine-language monitor. Underneath, it is something no 1980s machine could be: a single FPGA chip that implements the processor, video, sound and memory in reconfigurable logic, running at speeds and with memory sizes far beyond its ancestors. 

It is designed to be understood. Every register is documented, the schematics are published, and the documentation is freely licensed. A programmer can reach any part of the machine directly, from BASIC with POKE or from machine language, and nothing sits between the program and the hardware except what the program chooses to use. 

The MEGA65 is also three computers in one: 

- A MEGA65, with BASIC 65, 40.5 MHz processing, 256-colour graphics, four SIDs and digital audio. 
- A Commodore 65, the never-released successor to the C64, with its BASIC 10 when the original C65 ROM is installed. 
- A Commodore 64, able to run thousands of existing C64 games, utilities and applications.  

This book is about programming the first of these, and about using the other two where they help. It follows the plan of Raeto Colin West's Programming the Commodore 64: it starts with the machine and its BASIC, moves through machine language, and then covers graphics, sound, storage and peripherals in turn. 

#### From the C65 to the MEGA65 

In 1989 Commodore designed a successor to the C64: the Commodore 65, intended for release in 1990 (MEGA65 Book, p. 1-3). It combined a faster 4510 processor, a new VIC-III video chip with 80 columns and bitplane graphics, two SIDs (Wikipedia, “Commodore 65”), a built-in 3.5" floppy drive and BASIC 10, while keeping a C64 mode for compatibility. The machine never shipped. Prototypes and development units survived, but the C65 remained a collector's curiosity with an unfinished ROM. 

The MEGA65 project set out to finish it. Paul Gardner-Stephen and the MEGA Museum of Electronic Games & Art e.V. in Germany joined forces in 2014 and relaunched the project as the MEGA65 in 2015 (Dan Sanderson, “MEGA65: The First Ten Years”). A community of volunteers re-implemented the C65's custom chips in an FPGA, completed and extended the ROM, and designed a new case, keyboard and main board. Along the way the design grew: the 4510 became the 45GS02 with 32-bit operations and a 40.5 MHz top speed, the VIC-III became the VIC-IV, the SIDs became four, and attic RAM, digital audio and Ethernet were added. 

Production machines have shipped in several board revisions. The R3A boards were made in 2022 and the R6 boards in 2024; the differences that matter to programmers, such as the audio output on older boards, are noted where they arise (MEGA65 Book, pp. 2-7, V-26). 

Because the hardware is implemented in an FPGA, the MEGA65 can be upgraded by loading a new "core", the FPGA configuration, from its SD card. Cores, the ROM and the Hypervisor are updated separately and regularly. Throughout this book, details that depend on a particular version say so, and Chapter 11 explains how a program can find out what it is running on. 

#### The Three Modes 

Which machine the MEGA65 becomes at power-on depends on the ROM file on its SD card, and from there it can switch modes on request (MEGA65 Book, p. 11-3): 

|  Mode |  ROM |  BASIC |  Prompt shows |    
|  MEGA65 |  MEGA65 ROM (versions 92xxxx and later) |  BASIC 65 |  MEGA65 start-up screen |  
|  C65 |  Original Commodore 65 ROM (versions 91xxxx) |  BASIC 10 |  C65 start-up screen |  
|  C64 |  Built into either ROM |  BASIC 2 |  C64 start-up screen |    

The usual configuration is the MEGA65 ROM, which starts in MEGA65 mode, and that is the mode this book is written for. C65 mode is mainly of historical interest; almost everything BASIC 10 can do, BASIC 65 does better. 

##### Switching modes 

|  To |  How |    
|  C64 mode |  Type `GO64` and answer the confirmation; or hold MEGA while switching on or pressing reset |  
|  MEGA65 mode from C64 mode |  Type `SYS 58552`, which does not ask for confirmation; or press reset; or hold RESTORE briefly and press F5 in the Freezer |  
|  The machine-language monitor |  Type `MONITOR` in BASIC 65; or hold RUN/STOP while pressing reset |    

Any program in memory is lost when switching between MEGA65 and C64 modes, as on a C128 (MEGA65 Book, pp. 11-3, 11-4). Plugging a C64 cartridge into the expansion port before switching on also starts the machine in C64 mode (MEGA65 Book, p. 3-13). 

##### How compatible is C64 mode? 

C64 mode, often called GO64 mode, is a temporary reconfiguration of the MEGA65, not a separate computer. It inherits the C65's design, including its different CPU, and some C64 software does not run in it. All the MEGA65's own features remain present, including the Freezer, which can mount disk images. For the highest compatibility there is a separate option: the "C64 for MEGA65" FPGA core, which replaces the whole MEGA65 design with an accurate re-creation of the C64's chips (MEGA65 Book, pp. 3-13, 3-14). It is a different machine altogether, so nothing in this book applies to it. 

For programmers, the important point is the reverse: the MEGA65's features are not locked to MEGA65 mode. A program running in C64 mode can unlock the VIC-IV, use DMA or switch the CPU to full speed, using the techniques in Chapters 5 and 8.

|  Component |  MEGA65 |  Covered in |    
|  Processor |  45GS02, at 1, 2, 3.5 or 40.5 MHz |  Chapters 5, 7, 10 |  
|  Chip RAM |  384KB, visible to the video chip |  Chapter 5 |

The display requirements, connectors and RTC details come from the Book's set-up chapter (MEGA65 Book, pp. 2-3 to 2-7). The controller ports accept Commodore-compatible joysticks, paddles, the 1351 mouse and Amiga mice, and the IEC port accepts drives such as the 1541, 1571 and 1581, as well as SD2IEC and Pi1541 devices. 

Not everything the C64 had is here. There is no cassette port, so Chapter 14, which in West's book covered tape storage, covers the SD card instead. Nor is there a user port or a direct RS-232 interface in the C64 style; Chapter 17 covers the alternatives.

### Programming the MEGA65 — Chapter 5: MEGA65 Architecture 

Oct 4, 2026 · Updated Oct 11, 2026 · @Craig Taylor 

#### Introduction 

The MEGA65 is an 8-bit machine with a 28-bit address space, and almost everything interesting about programming it follows from that mismatch. A CPU that can only see 64KB at a time must reach 256MB of potential address space, three generations of video chip must share one set of registers, and a modern operating layer must sit underneath a Commodore-style ROM without getting in the way. 

BASIC 65 hides most of this. You can write substantial programs without ever thinking about where your variables live or which bank a bitmap occupies. But the moment you want to go faster, use more memory, mix BASIC with machine language, or understand why a POKE did nothing, you need a working model of the machine underneath. 

This chapter builds that model. It covers: 

- The 45GS02 processor and how its speed is controlled 
- The 28-bit address space and what lives where 
- The different kinds of RAM: chip RAM, attic RAM and colour RAM 
- The three banking mechanisms that decide what the CPU sees in its 64KB window 
- I/O personalities, which let one set of chips behave as a VIC-II, VIC-III or VIC-IV 
- The Hypervisor, DMAgic and the math accelerator  

Later chapters return to each of these in depth. Chapter 7 covers the 45GS02 instruction set, Chapter 8 covers machine-language techniques that depend on banking and DMA, and Chapter 12 covers the VIC-IV in detail. Here the aim is the big picture: enough to reason about the machine as a whole. 

A note on notation. Addresses the CPU sees directly are written as four hex digits, such as $D020. Full 28-bit addresses are written with seven hex digits, such as $FF80000. Where it helps, a 28-bit address may be split with a dot, as $FF8.0000, separating the megabyte from the offset within it. 

#### The 45GS02 Processor 

The 45GS02 is the latest member of a family that runs 6502 → 65CE02 → 4510 → 45GS02. Each step kept everything below it, so standard 6502 code runs unchanged, and the C65's 4510 code runs unchanged too. 

The 65CE02 contributed the features most visible to a 6502 programmer: a third index register, a relocatable zero page, a 16-bit stack pointer, 16-bit branches, and word increment and shift instructions. The 4510 added the MAP instruction for memory management. The 45GS02 adds 32-bit pointers, 32-bit arithmetic using a virtual register called Q, and the hooks that let the Hypervisor take control. 

##### Registers 

|  Register |  Width |  Purpose |    
|  A |  8 bits |  Accumulator |  
|  X |  8 bits |  Index register |  
|  Y |  8 bits |  Index register |  
|  Z |  8 bits |  Third index register, used by the (zp),Z and [zp],Z modes |  
|  B |  8 bits |  Base page: the high byte of the page used as zero page |  
|  SP |  8 or 16 bits |  Stack pointer; 16 bits when the E flag is clear |  
|  PC |  16 bits |  Program counter |  
|  P |  8 bits |  Status flags: N V E B D I Z C |  
|  Q |  32 bits |  Virtual register formed from A, X, Y and Z, with A as the low byte and Z as the high byte |    

The B register deserves a word of warning. On a 6502, zero page is always $0000-$00FF. On the 45GS02 it is whichever page B points to. B is zero after reset, so existing code behaves as expected, but a routine that changes B and forgets to restore it will break everything that uses zero page afterwards, including the KERNAL. 

The E flag occupies the bit that is unused on a 6502. When E is set, the stack behaves exactly as on a 6502, confined to page 1. When E is clear, the stack pointer is 16 bits wide and the stack can live anywhere in the 64KB the CPU currently sees. 

##### Speed 

The 45GS02 can run at four speeds: 

|  Speed |  Purpose |    
|  1 MHz |  C64 compatibility: 6502 cycle counts per instruction, though not exact access timing |  
|  2 MHz |  C128 fast mode compatibility |  
|  3.5 MHz |  C65 fast mode compatibility |  
|  40.5 MHz |  Full MEGA65 speed |    

MEGA65 mode starts at full speed. C64 mode starts at 1 MHz so that games, demos and loaders that count cycles behave as they would on a real C64. From C64 mode, POKE 0,65 switches to full speed, which is often the quickest way to make an old BASIC program dramatically faster. 

At 40.5 MHz, instruction cycle counts differ from the 6502's, so code that relies on exact timing must run at 1 MHz. Chapter 7 discusses timing, and the MEGA65 Book's instruction-set appendix gives the cycle counts. The practical consequence is simple: at full speed, code that was too slow in BASIC on a C64 is often fast enough on a MEGA65 without any machine language at all. 

#### The 28-Bit Address Space 

Every byte the MEGA65 can reach has a 28-bit address, giving a 256MB address space. Only a small part of it is populated, and the CPU never sees more than 64KB of it at once. The rest of this chapter is largely about how pieces of the 28-bit space are brought into that 64KB window. 

The C65 had a 20-bit, 1MB address space, divided into sixteen 64KB banks numbered 0 to 15. The MEGA65 keeps that arrangement for its first megabyte, so C65 software and BASIC 65's BANK command still make sense. Bank 0 is `$00000-$0FFFF`, bank 1 is `$10000-$1FFFF`, and so on. 

##### The memory map 

|  28-bit address |  Size |  Contents |    
|  `$0000000-$001FFFF` |  128KB |  Chip RAM, banks 0 and 1: the C65's original main memory |  
|  `$0020000-$003FFFF` |  128KB |  Chip RAM holding the system ROM, normally write-protected |  
|  `$0040000-$005FFFF` |  128KB |  Chip RAM, banks 4 and 5 |  
|  `$4000000` upward |  varies |  Cartridge port |  
|  `$8000000-$87FFFFF` |  8MB |  Attic RAM |  
|  `$FF80000-$FF87FFF` |  32KB |  Colour RAM |  
|  `$FFD0000-$FFD3FFF` |  16KB |  I/O, one 4KB block per personality |  
|  `$FFF8000-$FFFBFFF` |  16KB |  Hypervisor |    

Two details trip people up. First, the first 2KB of colour RAM also appears at `$001F800-$001FFFF`, where the C65 kept its colour RAM. Writes to that range go to colour RAM as well as the chip RAM underneath, and reads come from colour RAM, so it can't be used as ordinary chip RAM (mega65-core, `gs4510.vhdl`). Second, the ROM is not a separate chip: it is loaded into chip RAM at boot and then protected. Software that disables the protection can patch the ROM, or reclaim that 128KB as ordinary RAM. 

##### What the CPU sees 

The 16-bit addresses a program uses are translated into 28-bit addresses through several layers. In C64 mode the result is exactly the C64's memory map, controlled by the CPU port at $01: 

|  CPU address |  Default contents in C64 mode |    
|  `$0000-$9FFF` |  RAM |  
|  `$A000-$BFFF` |  C64 BASIC ROM |  
|  `$C000-$CFFF` |  RAM |  
|  `$D000-$DFFF` |  I/O |  
|  `$E000-$FFFF` |  C64 KERNAL ROM |    

In MEGA65 mode there is no single fixed layout. The KERNAL and BASIC 65 keep parts of the ROM mapped into the window and change the map as they run, reaching program text, variables and strings in other banks behind the scenes. Chapter 6 shows how. Any machine-language program is free to rearrange the view entirely. 

#### Kinds of Memory 

The MEGA65 has four kinds of memory, and they are not interchangeable. Each differs in speed, size and, most importantly, in what can see it. 

|  Memory |  Size |  CPU speed |  VIC-IV can see it |  Typical use |    
|  Chip RAM |  384KB |  Full speed |  Yes |  Programs, screens, bitmaps, sprites, character sets |  
|  Attic RAM |  8MB |  Slower |  No |  Bulk data, buffers, overlays, assets loaded once |  
|  Colour RAM |  32KB |  Full speed |  Colour data only |  Colour and attribute information for text screens |  
|  ROM |  128KB in chip RAM |  Full speed |  Yes |  KERNAL, BASIC 65, editor, DOS, character sets |    

##### Chip RAM 

Chip RAM lives inside the FPGA. The Book explains the name: it is the memory the CPU can reach at full speed (MEGA65 Book, memory chapter). Anything the VIC-IV must display, such as a screen, a bitmap, a character set or sprite data, has to be in chip RAM. Because it is internal it also runs at full CPU speed with no wait states. 

##### Attic RAM 

Attic RAM is 8MB of external memory on the main board. It is much larger than chip RAM but slower, and the VIC-IV cannot see it at all. The name suggests its role: a place to store things until they are needed. A game might keep all its levels in attic RAM and copy the current one into chip RAM with a DMA job. 

The CPU can reach attic RAM in two ways: through a 32-bit pointer using the `[zp],Z` addressing mode, or by mapping it into the 64KB window with MAP. For large transfers DMA is usually the better choice. Release boards, the development kit and Xemu have attic RAM, but the Nexys FPGA boards that can run the MEGA65 core do not, so software meant for every MEGA65 variant should check for it rather than assume it (MEGA65 Book, memory map appendix). 

##### Colour RAM 

On the C64, colour RAM is a separate 1KB of 4-bit memory at `$D800`. On the MEGA65 it is 8 bits wide and much larger, at `$FF80000`. The first 1KB still appears at `$D800` for compatibility, and the first 2KB is mirrored into bank 1 as described above. 

The extra width matters. In the VIC-IV's enhanced text modes each character cell uses two bytes of colour RAM, holding attributes such as blink, reverse, underline and alternate palette selection as well as the colour itself. Chapter 12 covers these modes. 

##### ROM 

The MEGA65 ROM is a 128KB image loaded from the SD card into chip RAM at `$20000-$3FFFF` when the machine starts. It contains the KERNAL, BASIC 65, the screen editor, the DOS and the character sets. Because it is really RAM, a different ROM version can be used simply by placing a different file on the SD card, and the C64-mode KERNAL and BASIC are part of the same image. 

#### Banking 

Three separate mechanisms decide what appears in the CPU's 64KB window, and a fourth lets the CPU bypass the window altogether. They come from the C64, the C65 and the MEGA65, and all of them are active at once. MAP takes precedence over every other banking mechanism (MEGA65 Book, p. K-7), but only for the 8KB blocks it actually maps. For every block MAP leaves unmapped, the older mechanisms decide: 

|  Order |  Mechanism |  Origin |  Applies to |    
|  1 |  MAP instruction |  4510 |  Each 8KB block it maps, with any offset |  
|  2 |  `$D030` ROM bits and the CPU port at `$01` |  C65 / VIC-III and C64 |  Fixed ROM and I/O areas in unmapped blocks; if either brings ROM into a region, ROM appears there |  
|  3 |  Nothing mapped |   |  Chip RAM in bank 0 |    

Flat 32-bit addressing sits outside this table: it ignores all three and goes straight to a 28-bit address. 

The interaction matters most in the `$A000-$BFFF` and `$E000-$FFFF` regions, where both `$D030` and `$01` can bring in ROM: if either is active and MAP does not map the block, the region shows ROM (MEGA65 Book, p. 14-39). 

##### The C64 CPU port 

Location `$01` works exactly as on the C64. Its low three bits, LORAM, HIRAM and CHAREN, choose whether BASIC ROM, KERNAL ROM, I/O and the character ROM appear in the window. The familiar values still apply: `$37` is the default, `$35` leaves only I/O visible above RAM, and `$34` gives RAM everywhere. This mechanism matters most in C64 mode, but it remains active underneath MEGA65 mode too. 

##### The `$D030` ROM bits 

The C65 added a register in the VIC-III, at `$D030`, that switches pieces of ROM into fixed places in the window. They show parts of ROM bank 2, which holds the C64-mode BASIC and KERNAL along with other ROM code; the MEGA65's main KERNAL, in bank 3, is reached through MAP instead. These regions are read-only, and MAP overrides them for any block it maps (MEGA65 Book, pp. K-6, K-7). 

|  Bit |  Name |  Effect when set |    
|  0 |  CRAM2K |  Shows the second kilobyte of colour RAM at `$DC00-$DFFF` |  
|  3 |  ROM8 |  `$28000-$29FFF` at `$8000-$9FFF` |  
|  4 |  ROMA |  `$2A000-$2BFFF` (C64 BASIC) at `$A000-$BFFF` |  
|  5 |  ROMC |  `$2C000-$2CFFF` at `$C000-$CFFF` |  
|  6 |  CROM9 |  Meant to select between the C64 and C65 character sets; not implemented on the MEGA65 |  
|  7 |  ROME |  `$2E000-$2FFFF` (C64 KERNAL) at `$E000-$FFFF` |    

Bits 1 and 2 are not banking bits: bit 1 enables external video sync (genlock), and bit 2 chooses whether colours 0-15 come from the palette ROM or palette RAM. The ROM-banking form of `$D030` exists only in the VIC-III and VIC-IV personalities, described in the next section; in the C64 personality, `$D030` is the C128's 2 MHz register instead. CRAM2K deserves a warning: while it is set, the CIA registers at `$DC00` and `$DD00` are replaced by colour RAM, so the keyboard can't be scanned and CIA interrupts can't be read or acknowledged, though the timers keep running (mega65-core, `iomapper.vhdl`). 

##### The MAP instruction 

MAP is the general-purpose mechanism. It divides the 64KB window into eight 8KB blocks and lets each block be redirected by adding an offset to its address. The lower four blocks, `$0000-$7FFF`, share one offset; the upper four, `$8000-$FFFF`, share another. 

MAP takes its arguments in the four registers: 

|  Register |  Bits 7-4 |  Bits 3-0 |    
|  A |  Lower offset, bits 15-12 |  Lower offset, bits 11-8 |  
|  X |  Enable blocks 3-0 (`$6000`, `$4000`, `$2000`, `$0000`) |  Lower offset, bits 19-16 |  
|  Y |  Upper offset, bits 15-12 |  Upper offset, bits 11-8 |  
|  Z |  Enable blocks 7-4 (`$E000`, `$C000`, `$A000`, `$8000`) |  Upper offset, bits 19-16 |    

The offset is added to the CPU address to form the physical address. To show bank 4 memory at `$44000-$45FFF` in the window at `$4000-$5FFF`, the offset is `$44000 - $4000 = $40000`, and only block 2 needs to be enabled: 
```
lda #$00        ; lower offset bits 15-8
ldx #$44        ; enable block 2 ($4000), offset bits 19-16 = 4
ldy #$00        ; upper offset bits 15-8
ldz #$00        ; no upper blocks mapped
map
eom
```

Two things about MAP are easy to get wrong. First, it sets both halves at once. The example above also unmaps anything the upper half was showing, including the KERNAL, so a real program must supply suitable values for Y and Z as well. Second, MAP blocks interrupts until the next EOM. EOM shares the 6502's NOP opcode, `$EA`, so the pair is always written together. 

The C65's MAP could only reach the first megabyte. The MEGA65 extends it with a megabyte selector. A MAP with X set to `$0F` loads A into bits 27-20 of the lower offset, and a MAP with Z set to `$0F` loads Y into bits 27-20 of the upper offset. A second MAP then sets the offset within that megabyte as usual. This is how attic RAM or the I/O personalities can be mapped into the window. 

##### Flat 32-bit addressing 

The simplest way to reach any byte is not to map it at all. The 45GS02's `[zp],Z` addressing mode takes a four-byte pointer from zero page and uses it as a 28-bit address, ignoring every banking mechanism above: 
```
ptr     = $fb
lda #$00
sta ptr
sta ptr+1
lda #$f8
sta ptr+2
lda #$0f
sta ptr+3       ; ptr = $0FF80000, start of colour RAM
ldz #$00
lda [ptr],z     ; read the first colour RAM byte
```

The assembler emits this as an EOM prefix before the ordinary `(zp),Z` instruction. It costs a couple of cycles more than a 16-bit indirect access, which is very little for the ability to reach any address without disturbing the map. For scattered accesses this is usually the best choice; for bulk copies, DMA is faster. 

#### I/O Personalities 

The `$D000-$DFFF` I/O area looks different depending on which machine the MEGA65 is pretending to be. This is called its I/O personality. A C64 program expects to find a VIC-II there and nothing else; a MEGA65 program wants the full VIC-IV register set, the DMA controller, the math unit and much more. Rather than compromise, the MEGA65 keeps a separate 4KB I/O view for each case and shows the CPU whichever one is selected. 

|  Personality |  28-bit address |  Visible at `$D000` |    
|  C64 |  `$FFD0000` |  VIC-II, SID, CIAs, colour RAM: what a C64 program expects |  
|  C65 |  `$FFD1000` |  Adds the VIC-III registers, including `$D030`, and the C65 DMA controller |  
|  MEGA65 with Ethernet |  `$FFD2000` |  MEGA65 registers, with the Ethernet buffers in place of part of the I/O area |  
|  MEGA65 |  `$FFD3000` |  Full VIC-IV register set and all MEGA65 devices |    

The split exists for compatibility. Many C64 programs write to I/O addresses that are unused on a real C64, sometimes deliberately and sometimes by accident. If those addresses held live VIC-IV registers, such programs would scramble the display. In the C64 personality those addresses do what they did on a C64, which is usually nothing. 

##### The knock 

The personality is changed by writing a two-byte "knock" sequence to `$D02F`, a register that does nothing on a real VIC-II. The same register exists in every personality, so the knock always works: 

|  Personality wanted |  Bytes to write to `$D02F` |    
|  VIC-III (C65) |  `$A5`, then `$96` |  
|  VIC-IV (MEGA65) |  `$47`, then `$53` |  
|  MEGA65 with Ethernet |  `$45`, then `$54` |  
|  VIC-II (C64) |  Any other value, such as `$00` |    

To unlock the VIC-IV from machine language: 
```
lda #$47
sta $d02f
lda #$53
sta $d02f
```

The VIC-IV bytes are the ASCII codes for "GS", and the Ethernet bytes spell "ET". MEGA65 mode starts with the VIC-IV personality already selected, so most MEGA65 programs never need the knock. It matters when you write code that starts in C64 mode, or when you need to be certain of the state after other software has run. 

The personality affects only what the CPU sees at `$D000-$DFFF`. It does not change the video hardware itself, and a flat 32-bit pointer can reach any personality's registers at its 28-bit address regardless of which one is selected. 

#### The Hypervisor 

Underneath the KERNAL runs a small, privileged program called the Hypervisor, often known by the name of its implementation, Hyppo. It is the first code to run at power-on, and it remains resident afterwards in its own 16KB of memory, which the CPU maps in at `$8000-$BFFF` only while in hypervisor mode and which ordinary programs cannot reach (MEGA65 Book, p. K-3). Only the serial monitor and debugger interface can still read it, through its 28-bit address. 

The idea comes from virtual machines on larger computers. The Hypervisor runs in a special CPU mode with access to everything, while the KERNAL, BASIC and user programs run in a normal mode that cannot see it. When something needs the Hypervisor's help, the CPU switches into hypervisor mode, the Hypervisor does its work, and control returns as though nothing had happened. 

##### What it does 

- Starts the machine. It initialises the hardware, reads the SD card, loads the ROM image into chip RAM and protects it, then starts the KERNAL. 
- Provides file services. It contains a FAT32 file system driver, so programs can read and write files on the SD card. 
- Manages disk images. It mounts D81 disk images so that the KERNAL and DOS see them as real floppy disks. 
- Runs the Freezer. Holding RESTORE enters the Freezer, which stops the running program, saves its complete state, and lets you inspect memory, change settings or swap disks before resuming.  

##### Hypervisor traps 

A program asks for a Hypervisor service by writing to one of the trap registers at `$D640-$D67F`. The write switches the CPU into hypervisor mode and jumps to the matching handler. The service number must be in A, and the trap is followed by a CLV instruction, because the CPU may or may not execute the byte after the trap when the service returns. On return, the carry flag is set if the call succeeded; if it is clear, A holds an error code (MEGA65 Book, pp. N-4, N-5). 

For example, this asks the Hypervisor for its version number using the general DOS trap at `$D640`: 
```
lda #$00        ; function: get version
sta $d640       ; trap into the Hypervisor
clv
bcc failed      ; carry clear means the call failed
```

The trap registers exist only in the MEGA65 I/O personalities, the normal one and the Ethernet one (mega65-core, `gs4510.vhdl`). Chapter 11 lists every Hypervisor function, and Chapter 14 shows how to use the file services to read and write SD card files directly. 

Because the Hypervisor saves and restores the complete machine state, a trap is safe to use from almost anywhere, including from inside a program that has remapped memory heavily. That same property is what makes the Freezer possible. 

#### DMAgic 

DMAgic is the MEGA65's DMA controller: hardware that copies and fills blocks of memory far faster than the CPU can, at 40.5MB per second for fills and 20.25MB per second for copies (MEGA65 Book, p. P-3). It was designed for the C65; on the MEGA65 it is built into the CPU, and it reaches the full 28-bit address space. 

DMAgic does not take commands through registers alone. Instead the program builds a small data structure in memory, called a DMA list, describing the job, then tells DMAgic where the list is. Writing the final byte of the list's address starts the job, and the CPU pauses until it finishes. 

##### The registers 

|  Register |  Purpose |    
|  `$D700` |  List address, bits 7-0. Writing here starts a job in the original C65 list format |  
|  `$D701` |  List address, bits 15-8 |  
|  `$D702` |  List address, bits 22-16: the bank holding the list |  
|  `$D703` |  Bit 0 selects the F018B list format instead of F018A |  
|  `$D704` |  List address, bits 27-20: the megabyte holding the list |  
|  `$D705` |  List address, bits 7-0. Writing here starts an enhanced job |    

An enhanced job is the normal choice on the MEGA65. Its list begins with option bytes, ended by `$00`, that extend what the job can do. The most useful options are: 

|  Option |  Meaning |    
|  `$0A` |  The list that follows uses the F018A format |  
|  `$0B` |  The list that follows uses the F018B format |  
|  `$80` nn |  Source address is in megabyte nn |  
|  `$81` nn |  Destination address is in megabyte nn |  
|  `$00` |  End of options |    

The megabyte options are what let a DMA job reach attic RAM at `$8000000` or colour RAM at `$FF80000`. 

##### A DMA list 

After the options comes the job itself. The low two bits of the command byte choose the operation: `%00` copy, `%01` mix, `%10` swap, `%11` fill. Only copy and fill are implemented on the MEGA65; the swap and mix codes are defined by the F018 format but do nothing useful (MEGA65 Book, pp. P-6, P-24). A copy needs a source; a fill uses the low byte of the source address as the fill value. 

This example clears an 80 by 25 text screen at `$0800` in bank 0 by filling its 2,000 bytes with spaces: 
```
lda #$00
sta $d702       ; list is in bank 0
sta $d704       ; list is in megabyte 0
lda #>list
sta $d701
lda #<list
sta $d705       ; start the enhanced job
rts

list    .byte $0a       ; option: F018A format
.byte $00       ; end of options
.byte $03       ; command: fill
.word 2000      ; byte count
.word $0020     ; source: fill value $20 in the low byte
.byte $00       ; source bank
.word $0800     ; destination address
.byte $00       ; destination bank
.word $0000     ; modulo, unused here
```

The same job in a loop of STA instructions would take thousands of cycles. DMAgic does it in a small fraction of that time, and BASIC 65 exposes the controller directly through its EDMA command. Chapter 8 covers chained jobs, modulo and skip options, and copying to and from attic RAM. 

#### The Math Accelerator 

The 6502 family has no multiply or divide instructions, and generations of programmers have written shift-and-add routines to make up for it. The MEGA65 instead provides a hardware multiplier and divider in the I/O area. You write two numbers into input registers and read the results back from output registers. 

Both units work on unsigned 32-bit inputs and share the same pair of inputs, so a single setup gives you both the product and the quotient. 

|  Register |  Size |  Contents |    
|  `$D770-$D773` |  32 bits |  MULTINA: first input |  
|  `$D774-$D777` |  32 bits |  MULTINB: second input |  
|  `$D778-$D77F` |  64 bits |  MULTOUT: MULTINA × MULTINB |  
|  `$D768-$D76B` |  32 bits |  DIVOUT fraction: fractional part of MULTINA ÷ MULTINB |  
|  `$D76C-$D76F` |  32 bits |  DIVOUT whole: integer part of MULTINA ÷ MULTINB |  
|  `$D70F` |  8 bits |  Status: bit 7 set while the divider is busy. Bit 6 (MULBUSY) is defined but currently never set, because the multiplier finishes in one cycle. Programs should still test it before reading MULTOUT, in case a future or slower implementation needs it |    

All values are little-endian, low byte first, as everywhere else on the 6502 family. 

##### Multiplying 

The multiplier is effectively instantaneous: by the time the CPU can read MULTOUT after writing an input, the product is ready. This multiplies two 16-bit values: 
```
lda #<1000
sta $d770
lda #>1000
sta $d771
lda #<300
sta $d774
lda #>300
sta $d775
lda #$00
sta $d772       ; clear the upper input bytes
sta $d773
sta $d776
sta $d777
lda $d778       ; product 300000 is now in $d778-$d77b
```

##### Dividing 

Division takes a few cycles longer. Wait for bit 7 of `$D70F` to clear before reading DIVOUT: 
```
wait    bit $d70f
bmi wait        ; bit 7 set: divider still busy
lda $d76c       ; integer part of the quotient
```

The fractional part makes the divider useful for fixed-point arithmetic, such as computing line slopes or scaling factors in graphics routines, without any floating-point code. If you need signed results, handle the sign yourself before and after, just as you would with a software routine. 

BASIC 65 programs can reach the accelerator with POKE and PEEK, but the real benefit is in machine language, where it replaces some of the most frequently written subroutines in 6502 programming with a handful of loads and stores. 

#### Summary 

The MEGA65 is easiest to understand as layers, built up from the C64 through the C65 to the MEGA65, and all still active: 

- The 45GS02 runs 6502 and 4510 code unchanged, adds a Z register, a movable base page, a 16-bit stack, 32-bit pointers and the 32-bit Q register, and runs at 1, 2, 3.5 or 40.5 MHz. 
- The 28-bit address space holds 384KB of chip RAM that the VIC-IV can see, 8MB of attic RAM that it cannot, 32KB of 8-bit colour RAM, a 128KB ROM loaded into chip RAM, the I/O personalities and the Hypervisor. 
- Banking decides what the CPU sees in its 64KB window. `$D030` and the C64 port at `$01` decide unmapped blocks; MAP takes precedence for the blocks it maps. Flat 32-bit addressing bypasses all three. 
- I/O personalities present a C64, C65 or MEGA65 view of `$D000-$DFFF`, selected by a knock sequence written to `$D02F`. 
- The Hypervisor boots the machine, provides SD card and disk image services through traps at `$D640-$D67F`, and runs the Freezer. 
- DMAgic copies and fills memory anywhere in the 28-bit space from a list in memory. 
- The math accelerator multiplies and divides 32-bit values in hardware.

### Programming the MEGA65 — Chapter 8: ML Methods Specific to the MEGA65 

Oct 4, 2026 · Updated Oct 11, 2026 · @Craig Taylor 

#### Introduction 

Chapter 7 described the 45GS02 in isolation. Real programs run on a machine full of state that someone else set up: the KERNAL's memory map, BASIC's choice of bank, the current I/O personality, the CPU speed, and interrupt handlers already installed. MEGA65 machine language is largely the craft of taking control of that state, changing it deliberately, and handing it back intact. 

This chapter collects the techniques that are specific to the MEGA65 rather than to the 6502 family in general: 

- A program skeleton that puts the machine into a known state 
- Controlling CPU speed 
- Using MAP to open windows into memory beyond the first 64KB 
- DMA beyond simple copies and fills 
- Raster interrupts 
- Loading files through the Hypervisor 
- Debugging with the monitor  

Two styles of program appear here. A cooperative program runs alongside BASIC and the KERNAL, called with SYS and returning with RTS; it must leave everything as it found it. A takeover program, such as a game or demo, replaces the system's map and interrupt handlers entirely and never returns. Most techniques apply to both, but where they differ the text says so. 

The examples use the same assembler syntax as Chapter 7: `.byte` and `.word` for data, `[zp],Z` for flat indirect addressing, and labels throughout. 

#### Taking Control 

A cooperative routine called by SYS starts in a known state: the mapping described in Chapter 6, with bank 0 low memory, the selected bank in the middle, and the KERNAL and I/O on top. Its only obligation is to restore anything it changes, including B, Z and the E flag, before RTS. 

A takeover program cannot rely on whatever state it inherits. Its first job is to set every banking mechanism, the I/O personality and the CPU state to values it chooses. The following skeleton does that, leaving all of bank 0 visible as RAM with I/O at `$D000`: 
```
start   sei             ; no interrupts while the machine changes
lda #$35
sta $01         ; C64 port: RAM everywhere except I/O

lda #$00
tax
tay
taz
map             ; MAP: no offsets, nothing mapped
eom

lda #$47
sta $d02f
lda #$53
sta $d02f       ; VIC-IV I/O personality

lda #$00
sta $d030       ; no C65 ROM banking
tab             ; base page = page 0
see             ; 8-bit stack in page 1
cld

lda #65
sta $00         ; full CPU speed

lda #$7f
sta $dc0d       ; disable CIA 1 interrupts
sta $dd0d       ; disable CIA 2 interrupts
lda $dc0d       ; acknowledge any pending
lda $dd0d
```

The order matters in three places: 

- Interrupts first. SEI comes before any change, because the KERNAL's interrupt handler assumes the KERNAL's map. An interrupt arriving halfway through would run with the ROM switched out. 
- Knock before `$D030`. The ROM-banking bits of `$D030` exist only in the VIC-III and VIC-IV personalities; in the VIC-II personality the address holds only the C128 2 MHz bit. So the knock must come first. MAP takes precedence over every other banking mechanism, but only for the 8KB blocks it maps (MEGA65 Book, p. K-7). The skeleton maps no blocks, so any ROM bits left set in `$D030` would still bring ROM into those areas; clearing `$D030` removes them. 
- All three banking mechanisms. Clearing MAP alone leaves `$01` and `$D030` in charge of every block MAP does not map. Only when all three are set does the program know exactly what it sees.  

The single MAP in the skeleton clears the offsets and block enables but not MAP's megabyte bytes, which only the two-MAP form described below changes. They are zero after reset and the KERNAL leaves them at zero, so this is normally safe (MEGA65 Book, p. 14-41); a program that may start after other software has used them can clear them first with `LDA #0 : LDX #$0F : LDY #0 : LDZ #$0F : MAP` before the skeleton's own MAP. 

The MEGA65 Book describes a fuller version of the same procedure for programs that want every byte of chip RAM. It also removes I/O from `$D000-$DFFF` by clearing bits 0-2 of `$01`, moves colour data so the first 2KB of colour RAM can be used as general memory, and disables the ROM write-protection on banks 2 and 3 (MEGA65 Book, pp. 14-39, 14-42). 

For that last step, use the Hypervisor's `rom_writeenable` service, which always leaves the ROM writable: 
```
lda #$02
sta $d641       ; rom_writeenable
clv             ; single-cycle instruction after the trap
```

The Book's example uses trap `$70` on `$D640` instead, but that service toggles the protection: if something has already switched it off, it switches it back on, and the program's writes to `$20000-$3FFFF` are then silently ignored. `LDA #$00 : STA $D641` turns the protection back on (MEGA65 Book, Hypervisor services appendix; mega65-core, Hyppo `mem.asm`). 

After this the program owns the machine. The KERNAL is gone, so the hardware vectors at `$FFFA-$FFFF` are now plain RAM in bank 0. The program must store its own NMI and IRQ vectors there before it executes CLI, as shown in the raster interrupt section below. The RESTORE key raises an NMI, so even a program with no use for NMIs needs a vector pointing at an RTI. 

As a starting point, place this skeleton after a BASIC header at `$2001`, as described in Chapter 6, so the program loads and runs with RUN. 

#### Controlling CPU Speed 

The MEGA65 inherited a speed control from each machine it is compatible with, and all of them still work. Two bits do most of the work in the VIC-III and VIC-IV personalities: FAST, bit 6 of `$D031`, and VFAST, bit 6 of `$D054`. 

|  Speed |  FAST (`$D031` bit 6) |  VFAST (`$D054` bit 6) |  Other |    
|  1 MHz |  0 |  0 |   |  
|  2 MHz |  0 |  0 |  C128 2 MHz bit set |  
|  3.5 MHz |  1 |  0 |   |  
|  40.5 MHz |  1 |  1 |   |    

The C128 bit is bit 0 of `$D030` in the VIC-II personality. In the C65 personality that address is the C65 banking register, which is one reason the personality matters when changing speed. 

##### The `$00` shortcut 

The CPU port's direction register at `$00` has a special meaning for two values. Writing `$41`, decimal 65, forces full speed regardless of the bits above. Writing `$40`, decimal 64, removes the force and returns control to them. Neither value changes the port's direction bits. This is the simplest method and works in every personality: 
```
lda #$41
sta $00         ; force 40.5 MHz
```

The CPU catches these values only when the write reaches address `$0000` with the normal mapping there. If MAP covers `$0000-$1FFF`, or the base page register B is not `$00` so that `sta $00` lands elsewhere, the shortcut does nothing, and a takeover program that maps the lowest block must use the bits below instead. 

##### Changing the bits directly 

To select a particular speed, release the force and set the bits. The 45GS02's TSB and TRB instructions set and clear bits in memory without disturbing the rest: 
```
lda #$40
sta $00         ; release forced full speed
trb $d054       ; VFAST off
tsb $d031       ; FAST on: 3.5 MHz
```

Writing to `$D031` has a side effect worth knowing. It is one of the VIC-IV's hot registers, along with `$D011`, `$D016`, `$D018` and the VIC bank bits of `$DD00`: any write to one of them, even writing back the value already there, recalculates all the VIC-IV's display settings from their VIC-II equivalents. FAST lives in `$D031`, so changing speed this way can undo a program's VIC-IV screen setup (MEGA65 Book, p. Q-17). Either clear HOTREG, bit 7 of `$D05D`, as described in Chapter 12, or change speed with the `$00` shortcut instead. 

From BASIC, `SPEED 1`, `SPEED 3` and `SPEED` select 1, 3.5 and 40.5 MHz, and FAST is a synonym; RSPEED reports the current speed as 1, 3 or 40. Both have no effect, and RSPEED reports wrongly, once `POKE 0,65` has forced full speed (MEGA65 Book, pp. B-106, B-225, B-245). 

##### Things that change speed for you 

A program cannot always assume the speed it set is the speed it gets. RUN/STOP-RESTORE resets the speed to 40.5 MHz (MEGA65 ROM change log), and the user can change speed in the Freezer. 

Nor is 1 MHz an exact copy of a C64. At 1, 2 and 3.5 MHz each instruction takes the 6502's number of cycles, but the memory accesses inside it may fall on different cycles, and timing can differ by up to about 7 microseconds. That is harmless for nearly all software, including many fast loaders, but tricks that depend on the exact cycle of a write, such as VIC-II variable screen positioning, are unlikely to work (MEGA65 Book, p. K-5). Timing-critical code should synchronise to the raster rather than counting cycles, at any speed. 

#### Practical MAP Techniques 

Chapter 5 described MAP's registers. This section shows how to use it for the most common job: opening an 8KB window onto memory outside the first megabyte, such as attic RAM. 

##### Choosing between MAP, flat addressing and DMA 

The three ways to reach distant memory suit different jobs: 

|  Method |  Best for |  Cost |    
|  Flat `[zp],Z` |  Scattered reads and writes |  Pointer setup; two extra cycles per load and three per store |  
|  DMA |  Moving or filling blocks |  Building a DMA list; CPU waits while it runs |  
|  MAP |  Running code from, or working intensively in, a region |  Changes what the CPU sees; affects every access in that block |    

MAP is the only one of the three that lets the CPU execute code held outside the 64KB window, and it lets ordinary absolute and indexed instructions work on distant data at full speed. 

##### A window onto attic RAM 

To make attic RAM at `$8000000` appear at `$4000-$5FFF`, the lower half needs megabyte `$80`, and an offset within that megabyte that turns CPU address `$4000` into `$00000`. That offset is `$00000 - $4000`, which wraps within 20 bits to `$FC000`. So A holds `$C0`, offset bits 15-8, and the low nibble of X holds `$F`, offset bits 19-16. Block 2 is enabled by bit 6 of X: 
```
lda #$80        ; megabyte $80: attic RAM
ldx #$0f        ; X = $0F: A selects the lower megabyte
ldy #$00
ldz #$00
map
lda #$c0        ; lower offset bits 15-8
ldx #$4f        ; enable block 2 ($4000), offset bits 19-16 = $F
ldy #$00
ldz #$00        ; upper half unmapped
map
eom
```

The megabyte selection persists until changed, so the second MAP sets the offset within megabyte `$80`. Only one EOM is needed, after the final MAP; interrupts stay blocked between the two. Moving the window is just a matter of repeating the second MAP with a different offset. To return to the first megabyte, select megabyte 0 the same way. 

In general, the offset for a window is `(target - window) AND $FFFFF`, where target is the address within the selected megabyte and window is the CPU address of the block. A takes offset bits 15-8, and the low nibble of X takes bits 19-16. Moving the window up by 8KB means adding `$2000` to the offset, so `$FC000` becomes `$FE000`, then `$00000`, and so on. 

##### Saving and restoring the map 

The 45GS02 has no instruction to read the current MAP settings back, but the Hypervisor does. Trap `$74`, hyppo_get_mapping, writes the MAP state, both halves including their megabyte bytes, as six bytes to a page-aligned address in the bottom 32KB of bank 0, with the page number in Y (MEGA65 Book, pp. 14-41, 14-42): 
```
ldy #$62        ; save the map at $6200-$6205
lda #$74        ; hyppo_get_mapping
sta $d640
clv
bcc error
```

A cooperative routine can use this to save the map it inherited, change it, and later restore it with the matching service, trap `$76`, hyppo_set_mapping, which loads the map from the same six-byte layout at page Y (MEGA65 Book, Appendix N). Flat addressing and DMA remain simpler when they suffice, since they leave the map alone, but MAP is no longer off-limits to code that must return cleanly to BASIC. A takeover program can still simply keep a copy of the values it last set. 

#### Advanced DMA 

Chapter 5 showed a single fill job. DMAgic fills memory at 40.5MB per second and copies at 20.25MB per second, against about 3.5MB and 1.7MB per second on a C65 (MEGA65 Book, p. P-3), so almost any bulk data movement is worth handing to it. This section covers the options that make it useful beyond simple blocks. 

All examples use enhanced jobs, started by writing the low byte of the list address to `$D705`, and the F018A list layout from Chapter 5: command, count, source, destination, modulo. Two details of the trigger registers matter. Writing the bank register `$D702` also clears the megabyte register `$D704`, so write `$D702` first and `$D704` after it. And BASIC 65 itself uses DMA to scroll the screen, so a program should rewrite all the list address registers before each job rather than assume they still hold its values (MEGA65 Book, pp. P-3, P-20, P-23). Two other triggers exist: `$D706` takes the list address in the current CPU memory map, and `$D707` runs a list placed directly after the instruction that triggers it, continuing execution after the list (MEGA65 Book, p. P-24). 

##### Reaching any megabyte 

The three address bytes in a DMA list cover only the first megabyte: low byte, high byte, and a bank in the low nibble of the third byte. Option `$80` sets the source megabyte and option `$81` the destination megabyte. This copies 16KB of level data from attic RAM at `$8010000` to bank 4: 
```
level   .byte $0a       ; F018A format
.byte $80, $80  ; source megabyte $80 (attic RAM)
.byte $81, $00  ; destination megabyte $00 (chip RAM)
.byte $00       ; end of options
.byte $00       ; command: copy
.word $4000     ; 16KB
.word $0000     ; source address within bank
.byte $01       ; source bank 1: $8010000
.word $0000     ; destination address within bank
.byte $04       ; destination bank 4: $0040000
.word $0000     ; modulo, unused
```

Addresses wrap within the selected megabyte during a job: a copy that runs past the end of a megabyte continues at its start. To let a long copy or fill cross a megabyte boundary, include option `$01` in the job, or set bit 1 of `$D703` to make that the default for every job. Both work from core 0.97 and are ignored in hypervisor mode (mega65-core, `gs4510.vhdl`; mega65-core PR #830). 

Colour RAM at `$FF80000` is reached the same way, with megabyte `$FF` and bank `$08`. 

##### Skipping bytes 

Normally DMAgic steps one byte at a time. Options `$83` and `$85` set the step, in whole bytes, for the source and destination. With a destination step of 80, a fill draws a vertical line down an 80-column text screen: 
```
vline   .byte $0a
.byte $85, 80   ; destination step: 80 bytes, one row
.byte $00
.byte $03       ; command: fill
.word 25        ; 25 rows
.word $00a0     ; fill with screen code $A0, a solid block
.byte $00
.word $0800+40  ; column 40 of the screen at $0800
.byte $00
.word $0000
```

Steps are useful wherever data is interleaved: a column of a screen or bitmap, every second byte of the two-byte colour RAM cells used by the VIC-IV's enhanced text modes, or one channel of interleaved sample data. 

##### Chaining jobs 

Bit 2 of the command byte marks a job as chained: when it finishes, DMAgic continues with the list that immediately follows, until it reaches a job without the chain bit. A single trigger can then perform a whole sequence of operations, such as clearing the screen, clearing colour RAM and copying in a new character set. In enhanced mode each job in the chain begins with its own option bytes, so each can use different megabytes and steps. Options carry over from one job to the next until the chain ends, though: a job that needs an option back at its default must set it again, because leaving it out does not reset it. 
```
clear   .byte $0a, $00  ; job 1 options: F018A, end
.byte $07       ; fill, chained (bit 2 set)
.word 2000
.word $0020     ; spaces
.byte $00
.word $0800
.byte $00
.word $0000
.byte $0a       ; job 2 options: F018A
.byte $81, $ff  ; destination megabyte $FF
.byte $00
.byte $03       ; fill, not chained: last job
.word 2000
.word $0001     ; colour 1, white
.byte $00
.word $0000
.byte $08       ; bank 8 of megabyte $FF: colour RAM
.word $0000
```

##### Transparency and line drawing 

The option list offers more than megabytes and steps (MEGA65 Book, p. P-14). Option `$07` turns on a transparent value and `$86` sets it: bytes equal to that value are skipped instead of copied, leaving the destination unchanged. That turns a DMA copy into a simple blitter for shapes with a background colour: 
```
blit    .byte $0a
.byte $07       ; enable transparency
.byte $86, $00  ; bytes of $00 are not written
.byte $00       ; end of options
.byte $00       ; command: copy
.word 64        ; one FCM character's 64 bytes
.word $2000     ; source $42000
.byte $04
.word $0040     ; destination $40040
.byte $04
.word $0000
```

Options `$82` and `$84` add fractional steps, in 256ths of a byte, which DMAgic uses for texture scaling, and options `$87` to `$8F` and `$97` to `$9F` configure a line-drawing mode that steps the destination or source along a slope. The Book quotes rates of up to 20 million pixels per second for scaling and 40 million for line drawing; its DMA chapter documents the parameters (MEGA65 Book, pp. P-13, P-14). On release 0.97 cores a line comes out two pixels shorter than its count, so add 2. Development cores fix this, let the direction bit reverse the major axis, and add line scaling through bit 4 of option `$8F` or `$9F` (mega65-core PR #887). 

Not every F018 operation exists. Only copy and fill are implemented: the command values for swap and mix, and the minterm bits that mix used, do nothing useful on the MEGA65 (MEGA65 Book, pp. P-6, P-24). 

##### DMA and the CPU 

The CPU stops while a job runs and resumes at the instruction after the trigger. There is no need to poll for completion, but because the DMA controller is part of the CPU, a job cannot be interrupted, and a long one delays interrupts too (MEGA65 Book, p. P-3). A raster interrupt that must fire on time should not compete with a very large transfer; split big jobs into pieces timed to fit between interrupts. The command byte has a bit documented as "yield to interrupts", bit 3, but the Book's own text says jobs cannot be interrupted, so do not rely on it. 

Audio DMA is the exception: it keeps playing during an ordinary job, stealing the cycles it needs from it, so sound does not stop while DMA runs (MEGA65 Book, p. P-3). 

#### Raster Interrupts 

A raster interrupt fires when the video chip reaches a chosen line of the display. It is the standard way to change colours, scroll registers or screen modes partway down the screen, and to run code once per frame at a steady rate. The VIC-IV supports the VIC-II's raster interrupt registers unchanged, so the C64 technique carries over. 

|  Register |  Purpose |    
|  `$D012` |  Raster compare, bits 7-0 |  
|  `$D011` bit 7 |  Raster compare, bit 8 |  
|  `$D01A` bit 0 |  Enable the raster interrupt |  
|  `$D019` bit 0 |  Raster interrupt has occurred; write 1 to acknowledge |    

##### A split-screen example 

This continues from the takeover skeleton earlier in the chapter, with interrupts disabled, CIA interrupts off and the KERNAL switched out. It installs its own vectors and changes the border colour at two raster lines, splitting the border into two colours: 
```
lda #<nmi
sta $fffa
lda #>nmi
sta $fffb
lda #<irq
sta $fffe
lda #>irq
sta $ffff

lda #$00
sta line        ; first interrupt at line 0
sta $d012
lda $d011
and #$7f        ; compare bit 8 = 0
sta $d011
lda #$01
sta $d01a       ; enable raster interrupt
sta $d019       ; clear any pending one
cli

main    jmp main        ; the main program runs here

irq     pha
lda line
bne lower
lda #$06        ; blue at the top
sta $d020
lda #$90
bra set
lower   lda #$02        ; red from line $90 down
sta $d020
lda #$00
set     sta line
sta $d012       ; next interrupt line
lda #$01
sta $d019       ; acknowledge
pla
rti

nmi     rti             ; ignore RESTORE

line    .byte 0
```

The handler alternates between two lines, setting the next compare value each time. It saves only A because it changes only A. A handler that uses X, Y or Z must save those too, and one that changes B must restore it before RTI. 

##### Stability 

On a C64, raster code at 1 MHz suffers from jitter: the interrupt can start a few cycles late depending on which instruction it interrupted, which shows as a ragged edge on colour changes. At 40.5 MHz the same few cycles are a tiny fraction of a scan line, so most raster effects are clean without the elaborate stabilisation C64 code needs. Code that runs at 1 MHz for compatibility still has the C64's jitter. 

The VIC-II-style registers count VIC-II raster lines. The VIC-IV also works in physical display lines, which allows finer positioning (MEGA65 Book, pp. Q-43, Q-44): 

|  Register |  Name |  Purpose |    
|  `$D052`, low bits of `$D053` |  FNRASTER |  Current physical raster line (read) |  
|  `$D053` bit 7 |  FNRST |  Reads back the compare mode: 0 physical, 1 VIC-II lines |  
|  `$D079`, low bits of `$D07A` |  RASCMP |  Physical raster compare value, used when the compare mode is physical |  
|  `$D07A` bit 6 |  EXTIRQS |  Enable extra interrupt sources, such as raster X position |  
|  `$D06F` bits 5-0 |  RASLINE0 |  First VIC-II raster line within the physical display |    

The compare mode is selected by FNRSTCMP, bit 7 of `$D07A`: clear for physical lines, set for VIC-II lines. FNRST reads back the same bit. There are roughly twice as many physical lines as VIC-II lines in the standard display, so a physical compare can split the screen between two VIC-II lines. 

##### Cooperative raster interrupts 

A program that keeps the KERNAL running can still use raster interrupts, by chaining into the KERNAL's handler instead of replacing the hardware vector. In C64 mode this works exactly as on a C64, through the vector at `$0314`, with the handler ending in a jump to the KERNAL's own handler so that keyboard scanning continues. Chapter 11 gives the equivalent MEGA65-mode vector. 

#### Loading Files Through the Hypervisor 

The KERNAL loads files from disk drives and disk images. The Hypervisor can load files straight from the SD card's FAT32 file system, without a disk image, and it works even when a takeover program has switched the KERNAL out. It can also load directly into attic RAM; the KERNAL can too only from ROM 920398, through SETBNK's 28-bit form. 

All Hypervisor services follow the same convention: put the service number in A, write it to `$D640`, and follow with CLV. The CPU may or may not execute the byte after the trap when the service returns, which is why a harmless CLV goes there; NOP also works, but it can act as a prefix to the next instruction, so CLV is safer. On return, carry set means success; carry clear means failure, with the error code in A. Registers not used to return values are preserved, and the trap register exists only in the MEGA65 I/O personality (MEGA65 Book, pp. N-4, N-5). The Book documents Hyppo version 1.2. 

##### The services 

|  A |  Service |  Inputs |    
|  `$2E` |  hyppo_setname |  Y: page of a zero-terminated ASCII file name |  
|  `$36` |  hyppo_loadfile |  X, Y, Z: bits 7-0, 15-8 and 23-16 of the load address in chip memory |  
|  `$3E` |  hyppo_loadfile_attic |  X, Y, Z: bits 7-0, 15-8 and 23-16 of the load address in attic RAM |    

hyppo_setname has strict requirements: the name must start on a page boundary somewhere in `$0000-$7E00`, must be shorter than 63 characters, and must end with a zero byte. Only Y is passed, the page number. The name is ASCII, and Hyppo does not convert from PETSCII; it also sets the Hypervisor's transfer area to that page as a side effect (MEGA65 Book, p. N-38). 

The load services load to `$00ZZYYXX` in chip memory or `$08ZZYYXX` in attic RAM, and can load files up to 16MB, wrapping around at the end of the 16MB range. The commonest failure is error `$88`, file not found in the current directory (MEGA65 Book, pp. N-27, N-28). 

##### Example: loading level data into bank 4 
```
load    ldy #>fname     ; page of the file name
lda #$2e        ; hyppo_setname
sta $d640
clv
bcc error

ldx #$00        ; load address $0040000
ldy #$00
ldz #$04
lda #$36        ; hyppo_loadfile
sta $d640
clv
bcc error
rts

error   ; A holds the error code, e.g. $88 file not found
rts

.align 256      ; the name must start a page (syntax varies)
fname   .text "LEVEL1.BIN", 0
```

The Hypervisor ignores case when it matches names, but it needs ASCII codes. Many assemblers' text directives produce PETSCII, which swaps the cases: a PETSCII directive such as ACME's `!pet` turns capitals into codes `$C1-$DA`, which the Hypervisor will not match. Use a directive that stores text unconverted (mega65-core, Hyppo `dos.asm`). 

The file is loaded exactly as stored. A file saved as a PRG carries a two-byte load address at the front, and the load call places those two bytes in memory too; for raw data it is simpler to save files without them. 

Hyppo reads files from the FAT32 file system on the SD cards, in the current directory; it does not read floppy disks or disk images (MEGA65 Book, p. N-38). Hypervisor services have changed between versions, and newer ones may not exist on an older Hypervisor, so a program that depends on them should check the version first with hyppo_getversion, service `$00`. 

#### Debugging 

Machine language fails silently: a wrong address or a missing RTS usually means a hung machine with no message. The MEGA65 offers several tools for finding out what happened, each suited to a different kind of problem. 

##### The built-in monitor 

The MONITOR introduced in Chapter 7 is an extended version of the C65's monitor (MEGA65 Book, p. O-6). Beyond assembling and disassembling, it can display and change registers, fill, compare, transfer and search memory, and load and save memory to disk. Because it understands 28-bit addresses, it can inspect attic RAM, colour RAM and the I/O personalities directly. The MEGA65 Book lists every command (MEGA65 Book, p. O-6). 

The simplest breakpoint is a BRK instruction. Place one where you want execution to stop, run the program, and the monitor appears with the registers as they were at that point. This works only while the KERNAL and its vectors are in place, because the KERNAL's BRK handler starts the monitor; a takeover program's BRK goes to its own interrupt handler. Replace the BRK with the original instruction afterwards. Check the stack pointer and B in the register display first: a wrong B or a runaway stack is a common cause of crashes. 

##### The border as a probe 

For timing problems and code that runs inside interrupts, the oldest trick still works best. An `INC $D020` at the start of a routine and a `DEC $D020` at the end turn the border a different colour while the routine runs. The height of the coloured band shows how much of the frame the routine takes, and a band that stops moving shows where a program has hung. 

##### The Freezer 

Holding RESTORE for about a second and releasing it stops any program and opens the Freezer, which saves the complete machine state. From there you can examine memory in the frozen program, change settings, or resume. This works even when a takeover program has disabled interrupts and switched the KERNAL out, because the Freezer runs under the Hypervisor rather than the KERNAL. 

##### Matrix Mode and remote debugging 

Matrix Mode is a debugging console run by a small helper processor in the core, separate from the main CPU; the Hypervisor only switches it on and off (mega65-core, `monitor_top.v`; MEGA65 Book, monitor appendix). Hold MEGA and press TAB to open it over the running display, and press the same combination again to close it. Because it runs on its own processor, it works even when the program has hung. Its R command, or just RETURN, shows all the CPU registers, including the MAPHI and MAPLO values that no instruction can read, which makes it the quickest way to see what a program has done to the memory map (MEGA65 Book, pp. 14-22, O-14). 

Matrix Mode can also step through a program. `t1` pauses the CPU in trace mode, and each press of RETURN then runs one instruction and shows the registers; `t0` lets the program run again. From core 0.97, interrupts are blocked while stepping with `t1`, so an IRQ does not take the step into the interrupt handler; `t2` pauses with interrupts still allowed. The `W` command sets a watchpoint that stops the program when a chosen byte is written (MEGA65 Book, monitor appendix; mega65-core PR #848). 

On release 0.97 cores, single-stepping or inspecting memory from Matrix Mode while a program runs INQ, DEQ or one of the Q register shift instructions can make the program skip a byte and crash; development cores fix this (mega65-core PR #943). The same console is available over a UART serial or JTAG connection, where cross-development tools on a PC can also load programs and inspect memory. 

For larger projects, a PC-based emulator with a debugger, such as Xemu, is often quicker still. Its monitor offers an execution breakpoint and a watchpoint that stops when a chosen byte changes, the fastest way to find out which piece of code is overwriting a variable; Matrix Mode's W command does the same on real hardware (Xemu; MEGA65 Book, monitor appendix). An emulator's timing may not match the hardware in every detail, so timing-critical code should always be checked on real hardware. 

#### Summary 

- Two styles. Cooperative routines start from the SYS mapping and must restore everything they change. Takeover programs set `$01`, MAP, the I/O personality, `$D030`, B and the stack themselves, then install their own vectors. MAP takes precedence over other banking, but only for the blocks it maps. 
- Speed. FAST in `$D031` and VFAST in `$D054` select 1, 3.5 or 40.5 MHz; writing `$41` or `$40` to `$00` forces or releases full speed, and BASIC has SPEED and RSPEED. `$D031` is a hot register. Slow modes match the 6502's cycle counts but not its exact access timing. 
- MAP. A megabyte selector followed by an offset opens an 8KB window anywhere, including attic RAM. MAP cannot be read by an instruction, but Hypervisor trap `$74` copies it to memory, and Matrix Mode shows it. 
- DMA. Megabyte options reach any memory, step options handle interleaved data, transparency makes a simple blitter, and chained jobs perform whole sequences from one trigger. Only copy and fill are implemented, and jobs cannot be interrupted, though audio DMA keeps playing. 
- Raster interrupts. The VIC-II registers work unchanged, and the VIC-IV adds compares in physical lines. At 40.5 MHz jitter is rarely a problem. Handlers must preserve every register they use, including Z and B. 
- Hypervisor files. hyppo_setname takes a page-aligned ASCII name in Y; hyppo_loadfile and hyppo_loadfile_attic load from the SD card into chip RAM or attic RAM, independent of the KERNAL. 
- Debugging. The monitor, BRK breakpoints, border probes, the Freezer, Matrix Mode and emulators each cover different kinds of failure.

##### Screen codes 

Screen codes are the values stored in screen memory, and are different from PETSCII. These are the codes of the upper-case character set; codes 128 to 255 are the same characters in reverse video.

#### Appendix C: Number Conversion 

Each hexadecimal digit stands for four binary digits, so conversion between the two needs only this table: 

|  Hex |  Binary |  Decimal |  Hex |  Binary |  Decimal |

To convert hex to decimal, multiply each digit by its place value and add:

#### Appendix F: Converting C64 and C65 Programs 

Many C64 programs run unchanged in C64 mode. Converting one to MEGA65 mode lets it use the MEGA65's speed, memory and graphics, but several differences need attention. 

##### BASIC programs 

|  C64 |  MEGA65 mode |    
|  BASIC starts at `$0801` |  BASIC starts at `$2001`; programs are relinked when loaded |  
|  Screen at `$0400`, 40 columns |  Screen at `$0800`, usually 80 columns; use PRINT, `T@&` and `C@&` rather than fixed addresses |  
|  Sprite pointers at 2040 (`$07F8`) |  Sprite pointers at `$0FF8` by default; better still, use SPRITE and MOVSPR |  
|  POKE to `$D000-$DFFF` |  Works when BANK is 128, the default |  
|  Variable names that contain BASIC 65 keywords |  Must be renamed: BASIC 65 has many more keywords, such as COLOR, PEN and BANK |  
|  Delay loops |  Run about forty times faster at 40.5 MHz; replace with SLEEP or VSYNC |  
|  `GET A$ : IF A$ = "" THEN ...` |  Works, or use GETKEY |  
|  Tokens |  C64 BASIC tokens mean the same in BASIC 65 |    

##### Machine-language programs 

- KERNAL calls through the standard jump table at `$FF81-$FFF3` work unchanged, as Chapter 11 describes. 
- Zero page and system RAM are laid out differently in MEGA65 mode; code that uses C64 zero-page locations or vectors other than the documented ones needs changing, or a private base page. 
- Memory map. Code that relies on the C64's `$01` banking should set it explicitly, and must allow for MAP and `$D030` as Chapter 5 describes. 
- Timing. Cycle-counted code runs at 1 MHz only in C64 mode or when the CPU is slowed; at full speed it needs raster synchronisation instead. 
- STZ. 65C02 code that uses STZ to store zero needs Z held at zero, as Chapter 7 explains. 
- I/O personality. C64 code expects the VIC-II personality; MEGA65 code that writes VIC-IV registers must knock first.  

##### C65 programs 

C65 BASIC 10 programs are close relatives of BASIC 65 and often run with small changes, mostly to graphics commands, which changed between BASIC 10 and BASIC 65. C65 machine language runs on the 45GS02, which executes every 4510 instruction.
